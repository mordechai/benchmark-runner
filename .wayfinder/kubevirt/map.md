# KubeVirt VM Backup/Restore for OADP

**Label:** `wayfinder:map`

## Destination

Full KubeVirt VM backup/restore support for the OADP workload, delivered in two phases. **Phase 1** integrates the battle-tested QE shell scripts (`VMsPopulation.sh`, `VMsAddDataVerify.sh`, `VMsEnableCBT.sh`, `VMsCBTstate.sh`) into the benchmark-runner scenario-driven flow so VMs can be created, verified, backed up, and restored via `tests.yaml` scenarios using the existing scripts as the population backend. **Phase 2** progressively absorbs those script capabilities into the native Python VM pipeline — cloud-init data generation, SSH key management, cloud-init removal, CBT, incremental data, enhanced verification — so the shell scripts become optional and the Python pipeline achieves full parity.

The map is done when: Linux VMs can be created via either script-based or native-Python paths, populated with data (dd baseline + increments, later FIO), backed up and restored via Velero's kubevirt plugin (both downstream OADP and upstream Velero), validated end-to-end including CBT and multi-disk scenarios, and live-test proven on a real cluster.

## Notes

- **Domain:** OpenShift Virtualization (CNV) + OADP/Velero backup
- **Skills:** `/grilling`, `/domain-modeling`, `/prototype` as needed
- **Repo:** `benchmark_runner/oadp/` — 13-mixin architecture with `vm_operations.py` and `vm_validation.py` already delivered
- **External scripts:** `/tmp/mpqe-scale-scripts/oadp-helpers/Scripts/` — 4 shell scripts (`VMsPopulation.sh`, `VMsAddDataVerify.sh`, `VMsEnableCBT.sh`, `VMsCBTstate.sh`) that are the operational standard for VM lifecycle
- **External dependency:** `/tmp/mpqe-scale-scripts` for test scenarios, ansible playbooks, and VM scripts; `/tmp/cnv-scenarios` as reference (not invoked)
- **`mpqe-scale-scripts` is a separate repo.** Local changes under `/tmp/mpqe-scale-scripts` are ephemeral — they persist only until the next clone/checkout. Any ticket that modifies files in that repo (shell scripts, `tests.yaml`, `dpa.yaml.j2`, ansible playbooks) must produce a commit and MR on the `mpqe-scale-scripts` repository to make the changes permanent. Tickets that require this are marked with `[mpqe-MR]`.
- **Cluster:** Available with CNV + OADP operator (E-04/E-05 resolved)
- **Phased approach:**
  - Phase 1 (script integration): wire shell scripts into the benchmark-runner flow via `vm_population_method: script` in scenario args
  - Phase 2 (native alignment): absorb script capabilities into Python — cloud-init data gen, SSH keys, cloud-init removal, CBT, incremental data, enhanced verification
- **Key constraints:**
  - Python VM pipeline stays (no delegation to cnv-scenarios)
  - Shell scripts are the reference implementation for Phase 1 — the Python pipeline aligns to their behavior in Phase 2
  - `-disks N` in `VMsPopulation.sh` means N **data disks** per VM; the OS disk (1 per VM, 60Gi) is always implicit
  - dd-based data fill first for script parity; FIO migration is a later Phase 2 step
  - Upstream Velero compatibility is a **Phase 2** concern — not required for Phase 1 (script-integration) completion; research can happen opportunistically in parallel, but implementation waits until Phase 1 wraps up
  - Multi-NIC/SR-IOV is out of scope

## Not yet specified

- **Scale testing results** — running 50+ VMs may surface throttling, CDI storm, or timeout issues that create new tickets
- **kube-burner binary packaging** — how/whether kube-burner gets into the benchmark-runner container image for the provider abstraction
- **Upstream kubevirt plugin installation path** — upstream Velero users must manually install the plugin; what's the documented config?
- **Integration test infrastructure** — what mock/stub environment do integration tests need? Does the test suite need a real cluster or can it work with mocked OC responses?
- **VMsPopulation.sh hardcoded cluster login** — the script has `ClusterLogin()` with hardcoded kubeconfig path (`/home/kni/clusterconfigs/auth/kubeconfig`); benchmark-runner manages its own auth — need to reconcile or bypass
- **Data disk size configurability** — `VMsPopulation.sh` hardcodes `DateDiskSize="150Gi"` and `DiskVolumeMode="Block"` — should these be parameterizable from tests.yaml or are they fixed for RHEL9 scenarios?
- **Script error handling** — the shell scripts use `sleep` timeouts between phases rather than polling; benchmark-runner may need to add polling wrappers around script invocation for reliability
- **`delete_oadp_custom_resources` race** — found during the ticket 006 live test: retrying a backup immediately after a manual `velero backup delete` can hit `"already exists"` because the helper returns before Velero's async deletion finishes. Not KubeVirt-specific (affects any plugin); not fixed as part of this map
- **CBT DataUpload granularity** — confirmed live that CBT-enabled kubevirt-datamover backups produce one `DataUpload` per VM (not per disk/PVC as in Flow1); not yet understood *why* structurally (datamover controller behavior), just observed
- **`/tmp/mpqe-scale-scripts` git corruption** — the local checkout's object database is missing blobs/trees (`git fsck` errors), same class of issue as the earlier `/tmp/br-venv` cleanup incident; not blocking anything today, but worth re-cloning before the next ticket that needs to commit/push changes there
- **Multi-namespace (`ns` > 1) live restore proof** — framework + unit coverage done in tickets 029/030; end-to-end live restore for `ns` > 1 (and Flow2 restore with `resourcePolicy`) still worth a cluster run
